# Implementation plan — architecture, workstreams, tests, checkpoints

Companion to `ARCHITECTURE.md` (what) and `ROADMAP.md` (when). This file
says **who builds which part, against which contract, how it is tested,
and where the owner can try each feature by hand**.

## 1. Increments

| Increment | Goal | Owner checkpoint at the end |
|---|---|---|
| 0 — walking skeleton (now) | five workstreams in parallel, each runnable on its own with tests and a `CHECKPOINT.md` | CP-A1…CP-E1 below |
| 1 — first end-to-end | frontend on the real backend; jobs with SSE; norm builder forms; slice detail with drivers; readiness gate | BPIC 2019 from upload to backlog in the browser; Table XI numbers on screen |
| 2 — the improvement loop | validation gates, findings, action cards, period comparison, governance pack export | hackathon O2C extract end-to-end; a pack exported with run ids |
| 3 — v1 start | assistant narration and Q&A over tools, knowledge-base tools, BPMN view with overlays, diff maps, server mode | assistant answers cite tables; BPMN overlays for the P2P template; `docker compose --profile team` |

## 2. Workstreams

| WS | Scope | Directory | Depends on | Produces |
|---|---|---|---|---|
| A — Backend core | domain, workspace storage (Parquet/DuckDB), metadata DB (SQLAlchemy/Alembic), engine adapter (only importer of `wise`), jobs table + worker, FastAPI `/api/v1`, CLI | `apps/backend` | `wise-pm` (local checkout), OpenAPI contract | service, CLI, tests, OpenAPI export |
| B — Frontend | Vite/React/TS app, generated client + MSW mocks from the contract, design tokens, context ribbon, journey rail, backlog explorer, slice detail, distribution lens, norm JSON view | `apps/frontend`, `packages/design-tokens`, `packages/api-schema` (generated client) | OpenAPI contract, later `@wise/flow` | SPA, component tests, e2e smoke |
| C — Analytics | `wise_analytics`: bootstrap/rank stability, contrastive gap decomposition, readiness gate, headroom, provenance records, synthetic generator | `packages/wise-analytics` | `wise-pm` | package, tests, docs |
| D — Knowledge | JSON Schemas, loaders, graph builder, lexical activity matching, P2P pack (BPIC 2019) and O2C pack (hackathon extract), datasets registry loader, CLI | `packages/process-knowledge` | `wise-pm` (templates validate), `datasets.yaml` | package, packs, tests, CLI |
| E — Flow library | `@wise/flow` core (model, abstract, ELK layout, layoutUnion, scales, overlays), `<ProcessMap/>`, Storybook, tests | separate repository `../wise-flow` | FlowGraph JSON contract | npm package (local link), stories |
| F — Integration and QA | contract drift, checkpoint verification, e2e on BPIC 2019 and the O2C extract, CI | root, `.github` | all | CI, reports |
| G — Assistant (increment 3) | provider, digests, tools, prompts, guardrails, cassettes | `apps/backend/src/wise_workbench/assistant`, `adapters/llm`, `adapters/knowledge` | A, D | — |
| H — Deployment (increment 2–3) | Dockerfiles, compose profiles, `uv tool` packaging | `docker`, `apps/backend` | A, B | images |

Rules for every workstream: edit only your directory; never import
`wise_workbench` from a package; no git commits (the owner commits); every
change ships with tests; a `CHECKPOINT.md` in the directory explains how a
person tries the feature, with commands and expected output; the
descriptive vocabulary of `CUSTOMER_JOURNEY.md` §8 applies to any text a
user can see.

## 3. Contracts between workstreams

| Contract | File | Producer → consumer |
|---|---|---|
| HTTP API | `packages/api-schema/openapi.yaml` (draft), regenerated by the backend (`wise-workbench openapi`) and diff-checked in CI | A → B; B mocks with MSW from the same file |
| FlowGraph JSON | `packages/api-schema/openapi.yaml` `#/components/schemas/FlowGraph` | A (`GET /runs/{id}/flow`) → E, B |
| Knowledge pack schema | `packages/process-knowledge/src/wise_knowledge/data/schema/*.json` | D → A (loader entry point `wise_workbench.knowledge`), B (glossary, failure modes) |
| Analytics results | typed dataclasses with `.table`, `.summary`, `.record` | C → A (analytics jobs) → B |
| Workspace layout | `ARCHITECTURE.md` §4 | A → F, H |
| Backlog column names | the library's `prioritize` columns (`n_cases, mean_score, gap, stable_gap, PI, stable_PI, …`) plus `keys`, `hotspot_type`, `dominant_layer`, `stability` | A → B |

## 4. Test strategy

| Layer | Tests | Oracle |
|---|---|---|
| Library | already green (85 tests); BPIC 2019 test with `WISE_BPIC19_CSV` | the paper's tables |
| Backend | unit (domain invariants, mapping parser, flow typing), adapter tests on temp workspaces (Parquet round-trips, DuckDB queries), job tests (lease expiry, crash and resume, cancel), API tests with `httpx` against the app, **golden run**: BPIC 2019 sample and the running example reproduce library outputs bit-for-bit | `wise` outputs; Table XI / XII numbers on the full log (opt-in, env var) |
| Frontend | Vitest + Testing Library for components; contract tests against MSW mocks generated from OpenAPI; Playwright smoke (upload → backlog) on mock and on the real backend | the contract; screenshots |
| Analytics | property tests (contrast decomposition sums exactly to the gap; bootstrap intervals cover the planted truth on synthetic logs at nominal rate; readiness flags planted artefacts); golden values on the running example | synthetic generator ground truth |
| Knowledge | JSON Schema validation of every pack in CI; template norms load with `Norm.from_dict` and pass `validate`; lexical matching of BPIC 2019 and hackathon labels reaches ≥ 90 % top-1 on the curated mapping | curated mappings |
| Flow | Vitest invariants (abstract keeps the graph connected, layoutUnion positions identical across filtered scenes, overlay geometry inside bounds); Storybook; Playwright visual regression | fixtures from BPIC 2019 |
| Cross-cutting | OpenAPI drift check; e2e BPIC 2019 reproduction in the UI; accessibility audit (axe) on main screens; bundle budget | — |

## 5. Owner checkpoints — how to try each feature

Every checkpoint lists the command, what appears, and the pass criterion.
Paths assume the workbench at `~/code/PhD/WISE/wise-workbench` and the
library checkout at `~/code/PhD/WISE/wise-lib`.

| CP | Feature | What you do | What you see | Pass when |

## 6. Definition of done (every increment)

Tests green in the workstream; `CHECKPOINT.md` current; OpenAPI regenerated
without drift; no `TODO`/`FIXME` left in shipped code; user-visible text in
`en` follows the vocabulary rules; accessibility check on new screens; the
owner has run the checkpoint.

## 7. Sequencing

Increment 0 runs the five workstreams in parallel (about two weeks of
engineering effort). Increment 1 integrates B on A and E into B (three
weeks). Increment 2 adds the loop (three weeks). Increment 3 opens v1.
